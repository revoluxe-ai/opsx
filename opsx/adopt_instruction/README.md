# Как готовить новый проект под OPSX

Этот каталог — инструкция онбординга. Исполняемая система читает машинный реестр `opsx/project/adoption/disabled-checks.yaml` и профиль `opsx/project/infra/infra-profile.yaml`, а не этот markdown в runtime.

Порядок:

1. Зафиксировать change и capabilities проекта.
2. Описать disposable-среду в `opsx/project/infra/infra-profile.yaml` (сервисы, порты, identity БД, tier-выражения). Не держать второе описание в командах и compose-комментариях.
3. Разложить тесты на active (hermetic) и infra (нужен ресурс). Маркер ресурса — из `test_tier_policy.py`.
4. Прогнать active-ворота. Всё, что падает и ещё не входит в spec, отключить записью реестра, а не правкой теста «чтобы стало зелёным» и не тихим skip.
5. Включать отключённое только change-ом, который задействует эту область. После зелёного прогона статус записи становится `enabled`.
6. Снять baseline подъёма и прогона (`opsx/project/infra/baselines.json`) отдельным живым прогоном, когда Owner явно разрешил smoke.

## Общая организация тестирования

[testing-policy.md](testing-policy.md) — общие правила adopt для всех проектов:
адресные проверки, полный unit-набор, отдельный infra-прогон, изоляция fixtures,
условия безопасного параллелизма и измерение скорости. Практика AdvBot приведена
как пример; конкретные команды и число workers определяет профиль проекта.

Этот раздел не поручает автоматически менять тесты, runner или настройки
текущего проекта. Необходимые изменения выделяются в отдельную задачу adopt.

Среда и порядок разрешённой квалификации: [infra-onboarding.md](infra-onboarding.md).
